# 液态玻璃空间采样修正（t53）

## 已定位，不只是插值问题

- CPU `LiquidRefraction.TryMap` 和内嵌 GPU HLSL 原来都从**岛中心**沿轮廓法线投射到外框。顶/底直线段的法线都相同，所有这些像素的 x 因而被折叠成同一中心 x；左/右边同理丢失各自 y。这能直接解释移动到色界两侧时整条边一起变色，双线性插值无法恢复已经丢掉的空间位置。
- 可控黑|黄 pad 上，旧版 254ce51 的顶边 x=80/160/240/320 都采到 `FFE0B030`；修正后分别为 `FF101010,FF101010,FFE0B030,FFE0B030`。
- 旧版将 R/G/B 分别从沿法线偏移的位置拼接；高对比边界上这本身就能制造输入不存在的彩色条纹。现在默认取消色散，所有通道共用完整 RGB footprint。高光也改为中性白，不为灰阶输入额外染蓝。
- 四条 BitBlt 捕获带的目的地范围本身正确，没有证据是只捕获一个点。但原代码把整个 DIB（包括从未写入的岛洞）复制出来，未检查 BitBlt 失败，也没有初始化 native DIB；流体斜率能把取样点推回空洞。不能从两张描述证明某一个截图噪点必然来自未初始化内存，但这条读未捕获区域的路径确实存在，已封堵。
- GDI 纯黑的 RGB/alpha 全 0 原来又被当作透明；GPU 在过滤后才猜 alpha，与 CPU 的逐像素猜法也不同。现在捕获时明确设置有效性：成功捕获的四带（包括纯黑）alpha=255，岛洞/自身遮挡 alpha=0 且 RGB 清零。

## 机制

每个轮廓像素从**自己的位置**沿局部 SDF 法线前进到捕获矩形外，不再从中心发射；保留切向坐标。当前形状的取样点经分段 pad 尺寸映射，映射前后都约束到有完整过滤足迹的捕获带。圆角、SDF 内沿、折射强度和流体形变保留。

每像素使用 5 个局部双线性 tap：中心与 x/y 四个 ±0.65px 邻点，共最多 20 个 texel 权重；不是整条边平均。先按 alpha 有效性加权，再统一归一化 RGB，无效 texel 不变黑、不串色。CPU 与 HLSL 同公式，流体纹理坐标也对齐 CPU 的 `(cols-1)/(rows-1)` 网格。

捕获一个后台任务；渲染另一个后台任务（GPU staging Map/readback、CPU warp/shade 均在此）。UI 只复制当前 pad/流体快照和显示冻结帧。每条流水线最多一帧运行、零帧排队，忙时保留最近完成帧，下一次提交最新形状，避免输入等待 GPU 和旧尺寸无界积压。此设计不是“每个屏幕刷新必定算完一帧”的性能承诺。设备不可用/丢失仍退回 CPU，约 10 秒后再尝试显卡；不按显卡名字筛选。DPI 缩放后的半径也转换到与捕获相同的物理像素坐标。

## 验证边界

`dotnet test tests/DynamicIsland.Core.Tests/DynamicIsland.Core.Tests.csproj -c Release`：223 测试。新增实际采样数学回归覆盖黑|黄、红|蓝、黑|白背景的四边多个空间点，移动分界/亚像素连续性、圆角/正负斜率、不同宽高 pad、清理捕获洞、透明垃圾 RGB 不污染有效颜色，以及独立流体快照。旧的中心发射数学不能通过空间点断言。

Windows CI 的 `build/check-glass-shader.ps1` 从 C# 提取**实际内嵌源**，用 Windows SDK `fxc /WX /Ges /O3` 编译 VS/PS 5.0 与 4.0。编译通过不等同于在 GPU 上实际运行，也不保证驱动行为和 CPU 逐像素位一致；尚无硬件 readback 对比。

本 box 的一次 Linux Release 合成算法探针：120 次 400×100 输入，纯 CPU 轮廓映射+五点采样总计约 527ms，平均约 4.39ms/次。**不含捕获、WPF、GPU 上传/读回、流体积分和真实桌面，不是 Windows FPS，也不是 RTX 3080 性能数据。** 真实 Windows（尤其外置 RTX 3080）、输入延迟、回退/热拔插仍待实测。

四带捕获看不到岛下面的实际桌面；展开/快速移动时会暂时复用并重映射最近一次捕获，背景可以有一帧或更多延迟。被自己遮挡或捕获失败的地方不猜造颜色；先保留最近完成帧。贴屏幕外区域可能表现为中性黑，不保证跨显示器/受保护内容捕获。没有改 DWM 材质、Window.Opacity、近黑皮肤、托盘或正式版本号。
